# T33 brand kit per project, and a Sample Weekly Show kit
Why: the API always loads Acme (`post_api/routes/enrich.py:65-66`, `routes/suggest.py:27-28`, duplicated `_kit_dir`).
The next real project is a work sample for a podcast host built from his weekly show "Sample Weekly Show" (Show), so the
kit must be chosen per project.
Read first: `post_core/model/` (Project), `graph/hashing.py` (`brand_kit_hash`), `recipes/instantiate.py`,
`post_api/routes/{enrich,suggest,projects}.py`, `brandkit/__main__.py` (`init`, `init --from`), `docs/BRAND-KIT.md`.
Build:
1. `Project.brand_kit: str` (kit id under `packages/brandkit/kits/`), default `"acme"` when absent so existing
   projects (`.demo*`) keep working. One shared helper (`post_api/brand.py` or in post_core) loads the project's kit;
   delete both `_kit_dir` copies. Workflows hash the project's kit, so switching kits makes branded nodes stale
   (visible, never silently regenerated).
2. CLI `post project set-kit <kit_id>` (refuses an unknown kit, lists the available ones); `PATCH /api/projects/{pid}`
   with `brand_kit`; `GET /api/brand-kits` lists kits with their status (from `brandkit status`).
3. Web: kit picker in the project header/settings showing the kit's name and status (filled vs guessed).
4. Kit content (free, one network fetch, run once by the agent doing this task): `brandkit init show --from
   https://example.com`. Every field stays flagged `guessed`; Travis reviews it (H6). Do not invent
   brand facts beyond what the site shows; Sample's face/voice are never brand assets.
Acceptance: pytest: project without `brand_kit` loads Acme; set-kit changes the hash and marks branded nodes stale;
unknown kit refused; API returns the project's kit in enrich/suggest context (tests use a temp kit dir). vitest for the
picker. `kits/show/design-system/` exists and `brandkit status show` reports it guessed. All suites green.
Out of scope: brand review (H6), per-cut kits.
